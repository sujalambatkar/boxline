# Performance: the utilisation report

This documents one deliberate exercise: a report that is easy to write and slow to run, measured, then made fast, with
what was measured at each step. Every figure below was produced by `scripts/perf.sh measure` on the machine and data described
here; the unedited output is in [`performance-run.txt`](performance-run.txt). Nothing is estimated or taken from elsewhere.

## The report

**Container utilisation by month and port.** For each month and location (a port or an inland depot):

| Column | Meaning |
|---|---|
| Movements | movement events recorded there that month |
| Containers | different containers with at least one movement there that month |
| Loaded / Discharged | load and discharge events |
| Utilisation % | Containers ÷ the whole fleet (25,200), to one decimal |

It also returns per-month totals for a chart (movements, different containers that moved anywhere, and the same as a % of the
fleet). It is served at `GET /api/reports/utilisation` (Ops only) and shown at **Reports** in the web app. Without a month range
it covers the latest twelve months, which is what the page asks for by default.

## Environment

| | |

| Load on the machine | 12 other containers were running (Kafka, MongoDB and others from unrelated projects) |

## Data

Generated by `scripts/perf.sh seed` into a separate database, `BoxLinePerf`, using `SqlBulkCopy`. The seeder only ever works on
a database whose name contains "Perf", so it cannot fill the development database.

| | |
|---|---|
| Container movements | **500,000** |
| Containers | 25,200 |
| Locations | 20 (16 ports, 4 inland depots; the busiest few carry most of the traffic) |
| Months | 25 (2024-11 to 2026-11) |
| Report groups (month × location) | 498 over all time, 238 for the last twelve months |
| Load time | 500,000 rows in 6.4 s (about 78,000 rows/s) with all indexes in place |

The data is synthetic but not random noise: each container goes through whole life-cycles (gate out empty → stuffed → gate in full
→ loaded → discharged → gate out full → delivered → empty returned), the next cycle starts where the previous one ended, and a unit
test runs every generated history through the application's own movement state machine.

## Method

- **Scenarios**, each run in its own process so memory is attributable to it:
  1. **naive EF**: loads every movement (with its container, change-tracked) into memory, filters, groups and pages in C#.
  2. **EF grouped**: still plain LINQ, but filtering, grouping, counting and paging happen in SQL Server and nothing is tracked.
  3. **stored procedure** (`usp_UtilisationByMonthAndPort`, as shipped): the same work in a procedure called through Dapper, one round trip.
- **Three request shapes**: `last12` (what the page sends: twelve months, first page of 20), `all` (no date range sent) and `wide`
  (every month of the data, 2024-01 to 2026-12, sent explicitly, as a date picker would). `all` and `wide` return the same 498 groups.
- **Index state**: measured with the covering index `IX_ContainerMovements_Report` **absent** and then **present**, so the effect of the
  index is separated from the effect of the code.
- **Cold run**: the SQL Server buffer cache is emptied first (`CHECKPOINT; DBCC DROPCLEANBUFFERS`), then one run is timed.
  **Warm runs**: 3 for the naive version (it is slow) and 5 for the others; the table shows the **median** (min to max in the raw file).
- Time is wall-clock for the whole call including materialising the result. Allocation is managed bytes allocated per run.
  Peak memory is the operating system's figure for the whole process (`/usr/bin/time -l`; about 85 MB is the bare runtime).
- A new `DbContext` per run, as a web request would have. The page is 20 rows.
- Correctness is checked separately: tests insert a hand-counted data set and require the naive, EF grouped and SQL versions to
  return identical rows, totals and monthly figures, for many filters, pages and month/year boundaries.

### What the numbers say

1. **Almost all of the gain comes from not loading everything into memory.** The naive report (1,463 ms) became 190 ms just by
   letting SQL Server do the filtering, grouping and paging through ordinary EF Core LINQ: **7.7× faster**, 806 MB → 0.3 MB allocated
   per request, and a process that peaks near 137 MB instead of 746 MB. The end result with the procedure and the index (134 ms) is
   **10.9× faster than the naive version** (9.8× against its best run), and 6.5× faster cold (413 ms vs 2,702 ms).
2. **The stored procedure is not meaningfully faster than a well-written LINQ query.** Without the index, EF grouped and the procedure are
   within 9% of each other (190 vs 189 ms; 196 vs 214 ms, the procedure being the slower one for all time). With the index the procedure
   is 12% faster for the last twelve months (134 vs 153 ms). Between the earlier trial run of this matrix and this one, the same
   configurations moved by up to about 10%, so differences of that size should not be over-read.
3. **The covering index helps the filtered request** (last twelve months: 189 → 134 ms, −29%, with 72% fewer page reads) **but made both
   unfiltered requests slower** (all time 214 → 265 ms and EF grouped 196 → 315 ms; the explicit wide range 104 → 189 ms), even though it
   cut page reads by about 38%. See the plans below. The page asks for twelve months by default, so the shipped behaviour is the good
   case, but this is a real trade-off, not a pure win.
4. **`all` and `wide` return identical results but are not equally fast without the index (214 vs 104 ms).** Both read the whole table
   with a parallel hash aggregate; `wide` shows 22 scans and 10,312 reads against 12 scans and 10,097. I have not isolated why they
   differ, and I would not conclude anything about which shape is generally faster from this one pair.
5. **Server-side paging made no measurable difference to time** here: the whole 498-row report on one page took 316 ms against 265 ms for
   the 20-row page (a difference inside this run's spread of 279–536 ms). What it changes is the payload: 2.2 MB allocated for 498 rows against
   0.2 MB for 20. With only a few hundred groups the aggregation dominates; paging pays off as the number of locations grows, which
   these data do not test.
6. The covering index is **24.6 MB** (against a 45 MB table) and took **0.3 s** to build after the data was loaded. The same index kept
   up to date *during* the bulk load ended up at about 57 MB (seed output), so building it after a large load is the better order.

## What the execution plans show

From `explain` (actual plans; the raw output has every operator).

- **No report index, any date range**: `Clustered Index Scan` of the whole table (500,000 rows, 10,097 reads), a **parallel `Hash Match`
  aggregate**, and a `Parallelism` exchange. A month filter cannot help: for the last twelve months SQL Server still reads all 500,000 rows
  and discards about 275,000 of them after reading. The monthly-totals statement scans the narrower `IX_ContainerMovements_ContainerId_OccurredAt_Id`
  index instead, but still reads every row.
- **Report index, last twelve months**: an **`Index Seek`** on `IX_ContainerMovements_Report` reads only the 224,540 rows in those months
  (the optimiser's estimate was exactly 224,540; the filtered statements use `OPTION (RECOMPILE)`, so it plans for the real dates), with **no sort** and **no key lookup** (the
  index covers every column used). A **`Stream Aggregate`** pair works through the rows in index order: the inner one collapses
  (month, location, container) to 63,373 rows, the outer one counts them into the 238 groups, which is how `COUNT(DISTINCT)` is produced
  without a hash table.
- **Report index, all time**: an `Index Scan` of the whole index, **serial** `Stream Aggregate`s, no parallelism. This is the plan the
  optimiser preferred (its cost estimate, 3.36, is lower than the 4.48 of the hash plan it replaced), but on this machine it ran
  slower, because the previous plan spread the work across several threads. I did not run a controlled experiment to prove that this is the
  cause; it is what the two plans show, and the timings are consistent with it.
- The **monthly totals** statement uses a `Hash Match` even with the index: its key order is (month, location, container), not (month,
  container), so a per-month distinct count across locations cannot stream.
- The row estimates for the scans are accurate; the optimiser over-estimates the number of groups (about 500 against 238), which is
  harmless here.

## What was changed, and why

| Change | Where | Why it matters |
|---|---|---|
| Persisted computed column `OccurredMonth` | `ContainerMovement` | month grouping and range filtering use a stored value and an index instead of evaluating `YEAR()`/`MONTH()` per row |
| Covering index `(OccurredMonth, LocationUnLocode, ContainerId) INCLUDE (EventType)` | migration | lets the report seek, stream and never touch the table |
| `usp_UtilisationByMonthAndPort` | migration, called through Dapper | one round trip returning the total, the requested page and the monthly totals (EF grouped needs five queries); `OPTION (RECOMPILE)` on the filtered statements so each date range gets its own plan instead of one sniffed from the first call |
| Paging with `OFFSET … FETCH` on a temp table | the procedure | only the requested rows are sent to the application |
| Default of the last twelve months | `UtilisationReportService` | the default request stays on the fast path however much history accumulates |

The naive version stays in the code (`NaiveUtilisationReport`), as the baseline and as the correctness oracle for the tests; so does the
intermediate `EfGroupedUtilisationReport`. Neither is registered for use by the API.

## Limits of this study

- **One machine, one data set, one kept run of the matrix.** An earlier run of the same matrix (not kept; the `wide` request did not exist
  yet) agreed in direction and size (e.g. procedure all-time 200 ms without the index and 265 ms with it, last twelve months 190 and
  136 ms). Medians of 3 to 5 warm runs; no statistical testing. Treat differences of roughly 10% as noise.
- **SQL Server ran under Rosetta emulation**, with other containers competing for the same CPUs. Absolute times will differ on native
  hardware or a server; the shape of the result (loading everything is the dominant cost; the index trades full-scan speed for
  range-seek speed) is the part worth trusting, not the milliseconds.
- **"Cold" is SQL Server's buffer cache only.** The Docker VM and macOS page caches were not emptied, so it is not a true cold disk read.
- **Write cost of the index was not measured** beyond storage (24.6 MB) and the bulk-load observation above. Every movement insert now
  maintains one more index.
- **Not tried**: a nonclustered columnstore index, a pre-aggregated summary table, forcing a hash aggregate or tuning `MAXDOP` for the
  all-time case, and data volumes other than 500,000 rows. They are the obvious next experiments; I have no numbers for them.
- The data is synthetic with 20 locations. A report with thousands of groups, or a skewed real workload, could behave differently.

## Reproduce it

```bash
scripts/start-db.sh          # SQL Server in Docker
scripts/perf.sh seed         # creates BoxLinePerf (about 10 s); refuses to run if it already holds movements
scripts/perf.sh measure      # the whole matrix, printed (redirect to a file to keep it)

# or step by step
dotnet run --project tools/BoxLine.PerfTool -c Release -- info
dotnet run --project tools/BoxLine.PerfTool -c Release -- indexes drop      # or create / status
dotnet run --project tools/BoxLine.PerfTool -c Release -- benchmark --scenario sql --range last12 --runs 5 --cold
dotnet run --project tools/BoxLine.PerfTool -c Release -- explain --range last12
```

`perf.sh` is macOS-specific (it uses `sysctl` and `/usr/bin/time -l`); the tool itself is plain .NET. The seeder never deletes data: to
re-seed, drop the `BoxLinePerf` database yourself.
